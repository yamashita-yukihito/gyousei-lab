# マージ前に直したい指摘

## 1. 優先度: 高
### FSRSへ渡す回答時刻と、履歴の再生順が一致しない

対象:

- `study_queue.py`
- `server.py`

`card_attempts` はDBの `id` 順で再生している一方、FSRSへ渡す時刻は `answered_at_client` を優先している。

そのため、次のような履歴が成立する。

1. 端末時計が進んだ状態で、未来の日付の回答を保存
2. 時計を直したあと、現在の日付の回答を保存
3. DB上は保存順に並ぶが、FSRSへ渡す時刻は未来→過去になる

py-fsrsはレビュー時刻を使って前回レビューからの経過日数を計算する。  
時刻が逆転しても必ず例外になるわけではなく、負の経過日数が短期復習扱いへ入り、誤った stability・difficulty・due を静かに作る可能性がある。

### 推奨修正

FSRSの正本時刻には、単調増加が保証されている `created_at_server` を使うのが安全。

`answered_at_client` は次の用途に限定する。

- 画面表示
- 利用時間の分析
- オフライン時刻の参考情報

クライアント時刻をFSRSへ使い続ける場合は、少なくとも以下が必要。

- タイムゾーン必須
- サーバー時刻との許容差を制限
- カード単位で時刻が逆行しないことを検証
- 遅延送信・端末時計変更の回帰テスト

また、現在の `parse_timestamp()` はタイムゾーンなしの値も受理する。  
後段ではタイムゾーンなしをUTCとして扱うため、日本時間のつもりで送ると9時間ずれる。

## 3. 優先度: 高〜中
### 「受験日より後へ期日を置かない」が完全には保証されていない

対象:

- `study_queue.py`
- `tests/test_study_queue.py`

現在は `EXAM_DATE = "2026-11-08"` をUTC午前0時として扱い、残日数を `maximum_interval` に渡している。

問題は次のとおり。

- 日本時間の試験開始時刻・終了時刻を表現していない
- 残り24時間未満でも `maximum_interval=1` になる
- py-fsrsの1分・10分などのlearning stepは、日単位のmaximum intervalとは別
- 試験直前のAgain / Goodなどで、試験時刻後のdueが作られる可能性がある
- 現在のテストはEasy中心で、直前の全Ratingを確認していない

### 推奨修正

日付だけでなく、タイムゾーン付きの試験時刻を定義する。

例:

```python
EXAM_AT = datetime(
    2026, 11, 8, 13, 0,
    tzinfo=ZoneInfo("Asia/Tokyo"),
).astimezone(timezone.utc)
```

さらに `review_card()` 後に最終防衛としてdueをclampする。

```python
card.due = min(card.due, EXAM_AT)
```

試験時刻以後は次回期日を作る意味がないため、以下のどれかを明示的に決めるべき。

- キューを終了扱いにする
- 期日を試験時刻へ固定する
- FSRS計算を止める

### 追加で確認すべき仕様

現在は、GETした「今」の残日数を過去の全回答のreplayへ適用する。

つまり回答履歴が増えていなくても、日が進むだけで過去のスケジュール全体が変化する。

これを「直前期に全カードを強制的に短い間隔へ戻す」仕様として意図しているならよいが、単に受験日越えを防ぎたいだけなら、各回答時点の残日数を使うほうが自然。

## 5. 優先度: 中
### `/api/study-queue` の入力検証に不整合がある

対象:

- `server.py`

### 5-1. deck識別子の競合

`studyDeckId=A&deckId=B` が渡された場合、片方を黙って採用する。

他のAPIやPOST側では競合を400にしているため、挙動が不統一。

### 5-2. Unicode数字で500になる可能性

`str.isdigit()` は一部のUnicode数字でもTrueになるが、`int()` が変換できない文字がある。

例:

```text
?limit=²
```

この場合、未処理の `ValueError` で500になる可能性がある。

### 推奨修正

```python
try:
    value = int(text)
except (TypeError, ValueError):
    raise ApiError(
        HTTPStatus.BAD_REQUEST,
        f"{name} must be an integer",
    )
```

`isdigit()` は使わず、変換自体を例外処理する。

# 設計として妥当な部分

## 復習を新規より優先する

復習がlimitを埋めた場合、新規が0枚になる設計は妥当。

復習は放置すると滞留し、新規は自分で増やす量を制御できる。  
新規を必ず数枚確保するより、復習優先のほうがFSRSの設計に合っている。

## 「絶対覚えた」の扱い

キューから外すだけで履歴とFSRS状態を消さない設計は妥当。

`uncertain` で解除すれば、過去の回答履歴から期日が復活する。

## fuzzingを切る

状態を保存せず、同じ履歴から毎回replayする設計では、fuzzingを切る判断は妥当。

同じ履歴なのにAPIを開くたびdueが揺れる状態を防げる。

## learningTypeに既定値を置かない

カード数が数百枚で、正本をGit管理しているプロジェクトでは、分類漏れをビルドエラーにするほうが安全。

## FSRS状態を専用テーブルへ保存しない

現在の規模なら妥当。

回答イベントを正本にし、FSRS状態を再計算できる構造は、派生状態の不整合を防ぎやすい。

ただし現在は毎回全履歴を読み込むため、履歴が数万〜数十万件になったら計測が必要。

重くなった場合も、最初からFSRS状態を正本化する必要はなく、次の順で改善できる。

1. 対象カード・対象deckだけSQLで読む
2. 最新resetより後だけ読む
3. 削除・再構築可能なキャッシュを置く
4. 履歴のcheckpointを置く

# FSRS実装の総合評価

## 結論

**FSRSをそれっぽく簡易再現している実装ではない。**

公式の `py-fsrs` ライブラリを使い、各回答を次の形へ変換して、ライブラリ本体の `Scheduler.review_card()` へ渡している。

- 誤答 → Again
- 正答・あてずっぽう → Hard
- 正答・たぶん → Good
- 正答・確信あり → Easy
- 正答・自信度なし → Good

その結果としてライブラリが生成した次の状態を使っている。

- due
- stability
- difficulty
- state
- last review
- review count

したがって、**FSRSアルゴリズムそのものを自作の簡易計算で代用しているわけではない。**

## 本格的にできている点

### 1. 正式なFSRS実装を利用している

`Scheduler`、`Card`、`Rating` を使い、レビューイベントを1件ずつ正式なAPIへ渡している。

独自に「正解なら3日後、間違いなら明日」のような簡易間隔計算をしているわけではない。

### 2. stability・difficultyを正式に更新している

FSRSの主要状態であるstability・difficultyは、py-fsrs側が正式に計算している。

アプリ側は結果を保存せず、表示用に取り出している。

### 3. 履歴replay方式は正攻法の一つ

回答ログから状態を再構築する方式自体は正当。

py-fsrsにもreview logからカードをrescheduleする考え方があり、履歴を日時順に再生して状態を再構築する設計はFSRSと矛盾しない。

### 4. fuzzing無効化の理由が明確

派生状態を保存しない以上、同じ履歴から毎回同じ期日を得たいという判断は合理的。

### 5. FSRSの4評価へ変換する設計も合理的

元のUIが○×だけなので、自信度を加えて4評価へ広げるのは自然。

特に「あてずっぽうの正解をGoodにしない」という判断は、復習間隔を伸ばしすぎないために有効。

### 6. 新規と復習を分けている

FSRSのdueカードを先に処理し、新規枚数に別上限を置く構成も実運用向き。

---

## 本格実装として不足している点

### 1. 履歴時刻の正規化が弱い

FSRSは時刻順が重要。

現在はDB順で再生しながらクライアント時刻を使っており、履歴順序の保証が不足している。

これはFSRSアルゴリズムの実装ミスではなく、**FSRSへ渡すイベントログの品質管理不足**。

### 2. ライブラリのバージョン固定が重要

FSRS状態を保存せず毎回再計算するため、ライブラリのバージョンや既定パラメータが変わると、同じ履歴から別のdueが出る可能性がある。

そのため、次は必須に近い。

- py-fsrsのバージョン固定
- 使用パラメータの固定
- バージョン更新時のmigration方針
- 代表履歴のgolden test

### 3. パラメータ最適化はまだしていない

現在は一般的な既定パラメータを使っている。

これは不正ではない。  
データが少ない初期段階では、既定パラメータを使うのが普通。

ただし回答履歴が十分たまったら、FSRS Optimizerで利用者固有のパラメータを学習する余地がある。

現時点では、無理に最適化するより履歴を正しく蓄積するほうが重要。

### 4. 受験日clampはFSRS標準機能ではなく独自仕様

「試験日より先へ出さない」は、通常の長期暗記FSRSではなく、この試験専用アプリの追加要件。

現在の方向性はよいが、日単位maximum intervalだけでは厳密ではない。

### 5. Rating変換は妥当だが、学習効果を測る必要がある

正答＋sureを毎回Easyにすると、利用者の「確信あり」の押し方によっては間隔が伸びやすい。

ただし試験日clampがあるため、極端な長期化は抑えられる。

今後確認したい指標:

- sure正解後の再正答率
- guess正解後の再正答率
- Again後の翌日正答率
- 予定日に出したカードの正答率
- desired retentionに対する実測保持率

## 総合判定

| 項目 | 評価 |
|---|---|
| FSRS本体 | 正式なpy-fsrsを使用 |
| 簡易的な自作再現か | いいえ |
| 4段階評価への変換 | 妥当 |
| 状態の再構築方式 | 妥当 |
| 新規・復習のキュー構成 | 妥当 |
| 履歴時刻の扱い | 修正が必要 |
| 試験日境界 | 修正が必要 |
| 依存バージョン固定 | 必須に近い |
| 個人パラメータ最適化 | 将来対応でよい |
| 現在の完成度 | 本格実装の土台はできているが、運用上重要な境界処理が未完成 |

一言でまとめると、**中身は本物のFSRSだが、FSRSへ渡す履歴と試験専用の境界処理をもう一段固める必要がある。**

「なんちゃってFSRS」ではない。  
ただし、マージ前に少なくとも以下は直したい。

1. FSRS時刻をserver時刻基準へする
2. py-fsrsのバージョンを固定する
3. 試験時刻でdueを最終clampする
4. 逆行時刻・遅延送信・試験直前のテストを追加する
5. deck resetをdeckごとに分離する

これらを直せば、個人用の行政書士学習アプリとしてかなり堅実なFSRS実装になる。
