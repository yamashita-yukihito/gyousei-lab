# 指示書：試験直前の教材総点検（クラウドセッション向け）

- 更新日: 2026-10-31
- 依頼元: 利用者と、利用者の Mac で gyousei-lab を扱う AI（Mac側AI）
- 依頼先: クラウドの Claude Code（ultracode）
- 状態: 未着手。進み具合は `docs/CLOUD_AUDIT_PROGRESS.md` に書く
- 結論: **学習カードと演習の誤りを、法令で確かめて潰す。** 新しい機能は作らない

## 0. 動き方（最初に読む）

- **利用者に質問しない。報告も求めない。** 利用者は試験勉強中で、AIとのやりとりに時間を使いたくない。迷ったら §3 の基準で自分で決め、決めたことを進捗ファイルに書く。
- **このセッションは、クレジット切れでいつ止まってもよい形で進める。** 下の「1バッチの進め方」を守る。
- **クレジットは使い切ってよい。** 利用者の希望である。節約のために点検を浅くしない。ultracode のワークフローと複数のエージェントを使い、バッチごとに点検役と検証役を分ける。
- **ただし、消費のためだけの変更をしない。** 文体の好みによる書き換えや、中身の変わらない整形はしない。点検の周回を重ねても誤りが見つからないなら、見つからなかったと書く。それも成果である。
- **期限：2026-11-05 23:59 JST。** ここを過ぎたら新しい変更を始めない。残り時間やクレジットが不明でも、上から順に進める。

### 1バッチの進め方

1. `git fetch origin` し、`origin/main` を作業ブランチへ merge する（Mac側で利用者が質問ノートを足し続けている）。rebase と force push はしない。
2. カードなら20枚前後、演習なら1章を点検し、§3 の基準で直す。
3. §4 の検査を通す。
4. `docs/CLOUD_AUDIT_PROGRESS.md` を更新し、コミットして、**すぐ push する。**

push 済みのコミットは、いつ取り込まれてもよいものだけにする。テストが落ちる状態や、1枚の修正の途中で push しない。

### ブランチ

- セッションに割り当てられたブランチがあれば、それを使う。なければ `claude/final-audit-20261031`。**main へ push しない。**
- 開始時に `git branch -r` と `docs/CLOUD_AUDIT_PROGRESS.md` を見る。前のセッションの続きがあれば、`claude/` の下のそのブランチを merge して、未点検のところから再開する。やり直さない。
- 使っているブランチ名を、進捗ファイルの先頭に書く。

## 1. なぜこの作業か

- 本試験は 2026-11-08。目標は6割（165〜190点の幅。`AGENTS.md` §5.4）。利用者は毎日カードと演習を回している。
- **いちばん害が大きいのは、教材の誤りをそのまま覚えること**である。2026-10-31 の点検でも、法律家の常識のページで条文に反する記述が見つかった。
- 法令基準日は `2026-04-01`。法改正は利用者が参考書で補うが、**教材の中に改正前の結論が残っていると、参考書の内容と食い違って害になる。**

### T6. 読みやすさのうち、利用者が決めたものだけ

`AGENTS.md` §5 の「主語と相手をなるべく省略しない」に反して、誰が誰に請求・主張できるのか読み取れない文を直す。対象は B・C・`correction`・`explanations`・演習の解説で、頻出度の高いカードから。A は直さない。**結論を変えない。分量を増やしすぎない。** §5.1 の範囲（処分性・原告適格・訴えの利益）は短いままにする。

### T7. クレジットが尽きるまで、別の目で点検を重ねる

T1〜T6 のあとは、次の順に周回する。前の周とは別のエージェントに、前の周の結論を見せずに判定させる。

1. **自分の修正の点検（必ず最初に）。** これまでの全修正を、修正理由を伏せて検証する。誤った修正は戻す。
2. 最頻出・頻出の76枚と、それに結びつく演習の問を、もう一度。
3. 残りのカードと演習を、もう一度。観点を変える（1周目が条文なら、次は判例の結論、その次は本番で受験生が間違える読み方）。

周回で直すのは法律上の誤りと §5 の規則違反だけにする。**文章の好みでは直さない。**

## 3. 直す基準

**誤った「修正」は、もとの誤りより害が大きい。** 試験前の1週間に、正しいものを壊さない。

| 区分 | 扱い |
|---|---|
| 条文に照らして明らかな誤り（条番号、数字、機関名） | 条文を e-Gov で確かめて直す |
| `correct` を裏返す修正 | 点検役と別の検証役の**2者が独立に**同じ結論を出し、条文または判例を確かめたときだけ直す。A と B・C・解説の全部を同じ作業でそろえる |
| 判例の結論 | 判例名と年月日が確かなときだけ直す。記憶だけで裏が取れないなら直さず、§5 に「要確認」と書く |
| 迷うもの、例外の細部 | 直さない。目標は6割で、例外の列挙で薄めない（§5.9） |
| 判例の細部（裁判官の内訳、下級審の量刑など） | 見ない（§5.0） |

- **条文の確かめ方。** `https://laws.e-gov.go.jp/api/1/articles;lawId=<ID>;article=<条>`（`scripts/drill_d/law.py` も使える）。基準日より後の改正が入っている可能性があるので、附則と施行日に注意する。
- **e-Gov に届かないときは**、条文の裏付けが取れないので、`correct` は裏返さず、数字も直さない。候補を §5 に書き、Mac側で確かめて適用する形にする。届かなかったことを進捗ファイルの先頭に書く。

## 5. してはいけないこと

- **触れない・使わないもの：** `production.sqlite3`、bundle、`server.py` の挙動、学習画面（`static/app.js`）、FSRS、localStorage の形式。この環境には非公開データもない。あると仮定しない。
- **カードの構造を変えない：** カードID、問ID、件数（カード314枚）、`frequency`、`sourceRefs`、`relatedPastQuestions`、`learningType`、`review` を変えない。カードの増減をしない。
- **A を変えない**（過去問の原文。§5）。
- **JSONを整形し直さない。** 利用者が同じファイルへ質問ノートを足し続けている。直した行だけが差分になるようにする。`git diff --stat` で確かめる。
- **public リポジトリである。** 新しく問題文や取得元の解説を貼らない。外部サイトの過去問を取得しない。秘密情報を書かない。
- **蒸し返さない（利用者の決定）：** 記述式の作り込み、カードの削減、商法の深掘り、holdout、§4.1・§5.4 の「やらない」と決めたもの。
- 新しいカード、新しい機能、依頼書 `docs/TECHNIQUE_SIMPLE_RULES_REQUEST_20261031.md` の優先度B（非公開データが要る）は、やらない。

## 6. 記録の形（`docs/CLOUD_AUDIT_PROGRESS.md`）

先頭を、**ここだけ読めば取り込めるように**保つ。

```markdown
# クラウド点検の進捗
- ブランチ: <名前>
- 最終更新: <JST>
- 状態: T2 行政法 80/125枚まで
- e-Gov: 届く／届かない
- 最後のテスト結果: <件数・成功か>

## Mac側でやること
- bundle の作り直しが要る: はい（カードを直したので）
- `correct` を裏返したカード: <ID と根拠>（Mac側でも条文を確かめる）
- ⑤との食い違いの可能性があるカード: <ID>
- 非公開データで確かめてほしいこと: <過去問の○×など>
- 要確認（直していないもの）: <場所・疑い・根拠>

## 修正の記録
| コミット | 場所 | 何を直したか | 根拠 | 検証 |

## 点検範囲
| 対象 | 周 | 結果（誤りの数） |
```

根拠には条番号または判例を書く。誤りが無かったバッチも、点検範囲に残す。

## 7. Mac側AIの取り込み手順（クラウドセッションはやらない）

利用者が「クラウドの点検を取り込んで」と言ったら、Mac側AIが行う。**途中の取り込みも可能**で、早いほど利用者が誤りを覚えずに済む。

1. `git fetch origin`、`docs/CLOUD_AUDIT_PROGRESS.md` の先頭を読み、差分の規模と `correct` を裏返したカードを確かめる。
2. 裏返したカードと数字の修正は、e-Gov で確かめ直す。おかしいものは取り込まない。
3. 全テスト（非公開データありで `test_variant_a_matches_source` と `test_card_frequency_audit` も走る）。`validate_card` を全カードへ。演習は `build.py <科目>` と `minpo_extra.py` で章ファイルと `chapters.json` の差分がないかを見る。`measure.py --check`。
4. main へ取り込み、bundle を作り直して差し替える（`AGENTS.md` §5.0 の手順、件数のfail closed）。
5. 非公開データで確かめる項目を処理し、結果を利用者へ短く報告する。
6. カード動画の作り直しは、`correct` が変わった回だけにする。全部で2時間かかるので、利用者の時間を取らない形で流す。
7. **11/7・11/8 は本番の画面を触らない。** 11/6 までに終える。
